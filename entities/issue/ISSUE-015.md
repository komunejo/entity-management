**The report.** In the same correspondence that produced [the wikilink reference carries its ID in the destination, not in the text the reader sees (ISSUE-014)](ISSUE-014.md): the reporting space staged a copy of what it calls "the canonical store" — 240 slug-keyed memory records — as a 0.7.0 `filename: free` project. Over a hundred records error twice each. The records keep their `type` inside a nested `metadata:` block; the schema language declares fields only at the frontmatter's top level, so `metadata` lands as an unknown field and the required `type` as missing — two errors per record for one dialect difference. The reporter's proposed remedy is a flatten migration. The run also told the reporters something about their own estate they did not know: their two agents' stores use different frontmatter dialects, and the canonical store is itself mixed — 71 records nested, 154 flat.

**What the analysis established.** The nested layout is the format Claude Code prescribes for its memory stores — prescribed operationally, in instructions the harness injects into sessions, but publicly undocumented: no published schema, no stated rationale for the nesting, no contract for the enums (`type`'s values exist only in the injected prompt; `node_type` is fixed nowhere), and observed drift without notice — a `modified` key appeared in v2.1.214, and live specimens carry keys the injected specification never mentions. The wrapper itself adds nothing: a frontmatter block already *is* the document's metadata, so a `metadata:` block inside it is metadata about metadata — and a nested mapping is not even editable in Obsidian's Properties, [the second tier of this project's own support criterion (ISSUE-014)](ISSUE-014.md). Two consequences follow. The surface defect is trivially soluble wherever the corpus is a conversion: drop the wrapper, lift its fields to the top level, lose nothing. And the underlying defect is not the engine's to fix: a schema cannot be *deduced* from a format whose owner never committed to one. Against an uncontracted, silently drifting source — the 71/154 mix is that drift's fossil record — every validation error is undecidable: is the record wrong, or did the format move? A schema copied from a moving target grants confidence without foundation, which is worse than no schema. The answer that fits this project's charter: the adopting owner *declares* the schema — the structure is the user's to define, deduction was never the offer — and the conversion is the adaptation layer that absorbs the source's drift. The general question the wrapper raised — when nesting in frontmatter is ever the right design — is spun off on its own terms as [nested metadata: one legitimate client (the compound value), two impostors (embedded entities, interaction history) (PROP-009)](../proposal/PROP-009.md).

**Why this stays open without a design.** What blocks resolution is not a missing capability but a missing problem statement. The report does not say what "the canonical store" is: the directory as the harness writes it, or a consolidation the reporters maintain and write themselves. The letter's own phrasing — the two agents' stores in different dialects, *and* the canonical store *itself* mixed — reads most naturally as a third, consolidated store, in which case the mix is the reporters' own hygiene, the writer is within their reach, and no engine change is implied at all; but that is an inference from one sentence, not a datum. If instead the harness writes it, adoption needs a standing conversion layer against an uncontracted source, and the diagnosis lands differently. Pending with the reporter before any design is fixed: what the canonical store is and who writes to it; and whether its records carry IDs at all (the same question [ISSUE-014](ISSUE-014.md) leaves pending for the link migration). A fourth finding of the same report — thirteen non-record files (topic indexes, profiles, the store's own mandatory index) erroring inside the staged layout — dissolves under the engine's spatial freedom and is registered nowhere else: in a conversion the layout is the owner's, so records go into a declared location and free files stay outside it — zero errors, today's engine. It would survive only in an in-place validation of a layout the owner cannot rearrange (the same pending question), and the ground it would then touch — per-file placement and exemption — is already held by the placement family: [a record named like its own directory disappears without a word (ISSUE-007)](ISSUE-007.md), [container directories cannot carry their own typed record (ISSUE-009)](ISSUE-009.md), [folder notes as first-class typed records across a whole space (ISSUE-010)](ISSUE-010.md). Held open on purpose, so the finding reads as what it is: not unsolved for lack of knowledge, but unsolvable as posed — what is missing is not a remedy, it is the problem statement.
