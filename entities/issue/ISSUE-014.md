**The problem.** The engine validates wikilinks in exactly one form: `[[ID]]`, with `[[ID|alias]]` accepted alongside it. That form only works where files are named by their IDs — this registry's own `filename: prefixed` mode. Reported from the field, in the same correspondence that confirmed same-day adoption of 0.7.0: a reporting space staged a 240-record store as a `filename: free` project — files named by legible slugs — and its 170 `[[slug]]` cross-references, "the store's connective tissue," validated as nothing. In a slug-named store the one validated form is unusable (`[[ID]]` points at a file that does not exist there) and the form actually written is invisible. Wikilinks and validation cannot meet.

**Where the report's own reading goes wrong.** The reporter concluded a dichotomy: leave the store's most important links unvalidated, or rewrite them into ID form when "the legible slugs are the feature." The dichotomy is false — in the labeled reference form the slug is precisely what stays visible, as the label. What the engine lacks is not a reason to choose between validation and legibility; it is a wikilink form worth migrating to.

**Where this project went wrong.** The pattern demands the ID in the wikilink's *destination* slot, and that slot natively names the file — `[[file|alias]]` is the construct's own grammar. The pattern was written in and for this registry, which is `filename: prefixed`: here the file is named by its ID, so `[[ISSUE-012]]` is simultaneously `[[file]]` and a visible ID, and the coincidence was taken for the rule. `filename: free` splits the two roles and exposes which one the slot actually holds — the file. One filename mode measured, presented as the class: the third instance of the error shape [the ' #' rule fires on benign comments, and for typed fields its remedy is impossible (ISSUE-013)](ISSUE-013.md) records against the scan's evidence base and [a prose reference is one link whose text carries the ID (DEC-022)](../decision/DEC-022.md) records against DEC-017's single renderer. It also inverts DEC-022's own doctrine: the text the reader sees carries the decision, and the alias — the text the reader sees — is exactly the part the validator never reads.

**The rule, and the cases it decides.** The owner's ruling, recorded as the design's fixed point: in every link form, the destination names the file and the visible text is what opts into the reference convention — bare ID or `label (ID)` — so a reader always knows what is being referred to. Case by case:

- `[[file|label (ID)]]` — validates as a reference: ID resolved, destination checked against the ID's file the way the Markdown form's path is. New; today it passes in silence.
- `[[file|ID]]` — the same reference, unlabeled.
- `[[ID]]` bare — stays valid: the destination doubles as the visible text and shows the ID. Meaningful only where the file is named by its ID.
- `[[slug]]` bare — ordinary prose the engine has no opinion about, and the why is the project's charter, not a technicality: this skill exists to bring structure to a format that has none by default, the structure is the owner's to define and deliberately partial, and coherence in prose is what a project *buys by adopting* the visible-text convention — never something the engine imposes on prose that adopted nothing. The mirror of DEC-022's undeclared-prefix boundary, and the reason the reported 170 links stay invisible rather than going red until they are migrated.
- `[[ID|alias]]` with no ID in the alias — never a form of its own: it is `[[file|alias]]` in the one mode where the file happens to be the ID, and its visible text shows the reader no ID, so under the rule it is ordinary prose. It is validated today, so this is a contract change, and [contract changes are never silent (REQ-006)](../requirement/REQ-006.md): the transition wants the loud treatment the caret got, with the explicit migration `[[file|label]]` → `[[file|label (ID)]]` for the links that were meant as references.

**The support criterion**, also the owner's ruling: cumulative. CommonMark is the minimum standard — every record must survive a converter that speaks nothing else, which is what DEC-022 bought and this issue must not spend. Wikilinks are the second tier, required not by standard but by adoption: Obsidian and its kin are how a large class of registries are actually worked, even though other editors (Typora among them, the one this registry is worked in) render `[[...]]` as literal brackets. The engine detects both forms as equals; a project's preference between them is style, not grammar.

**Open at registration.** To be measured before the design lands, on the class and not the sample: Pandoc's wikilink extensions (`wikilinks_title_after_pipe` and kin) and mistletoe against the alias-carrying-ID form — a validated form that shatters in the transformation targets would repeat the caret's mistake in a new dialect. The adoption path for a corpus already written in `[[slug]]`: a migration utility into whichever form lands, which presupposes the store's records carry IDs at all (question pending with the reporter), and which holds coverage only together with a change in the writing convention — a one-pass migration of a corpus that keeps being written the old way buys coverage that decays from the first new record. And noted while reading, not this issue's to settle: DEC-017 ruled wikilinks opt-in by project declaration; the engine as shipped accepts them everywhere, no declaration asked.
